# ESG-Insight Agent：从 0 到 1 的思考与构建

> 本文档记录整个项目的**思考链路与设计决策**，从"为什么做"到"怎么做"到"做了什么"，按时间线展开。可直接用于面试讲述。
>
> **项目定位**：一个完整的 Agent 质量工程实战项目，覆盖 **AI 应用开发（12-15级）+ AI 评测（13-16级）** 的核心能力要求。

---

## 一、起点：为什么是 ESG 报告分析？

### 1.1 背景 —— 我的双重知识结构

我本科是**金融工程 + 计算机科学与技术**双学位。这意味着：

- 我能读懂财报、理解财务指标背后的商业逻辑；
- 我能写代码、设计系统、理解 AI 的边界。

在金融证券公司的实习中，我大量接触过各类企业披露文件：

- **年报/财报**：以三张表（资产负债表、利润表、现金流量表）为核心，结构高度标准化，数字是主角。
- **招股说明书**：格式受证监会严格约束，关键信息有固定章节。
- **债券募集说明书**：强调偿债能力和担保措施。
- **ESG 报告**（环境、社会与治理报告）：**完全不同的物种**——动辄 100+ 页，大段大段的文字描述，格式因公司而异，没有统一模板。

前几类文件的自动化分析工具已经相当成熟（Wind、同花顺等数据终端可以直接导出结构化数据），但 ESG 报告的分析，市场上至今缺乏一个真正好用的工具。

### 1.2 为什么 ESG 报告"值得被分析"

"值得"有三个层面的理由：

**第一，宏观趋势。** 绿色经济、碳中和、可持续发展是全球共识。中国在 2020 年提出"双碳"目标，欧盟推出碳边境调节机制（CBAM），ESG 评级直接影响企业融资成本和出口竞争力。ESG 报告不再是一份"面子工程"，而是一份逐渐具有**实质性财务影响**的文件。

**第二，信息密度低，但价值密度高。** ESG 报告不像财务报告——财务报告的核心是数字，格式固定，批量处理容易。ESG 报告常常是：

- 讲理念："我们致力于绿色低碳发展……"
- 讲愿景："力争 2030 年实现碳达峰……"
- 讲案例："某工厂引进了节能设备……"

有用信息被淹没在大段的公关话术里，**但一旦提取出来，就极具分析价值**——碳排放数据、绿色金融规模、供应链劳工标准、董事会多样性……这些指标直接关联企业的长期风险和竞争力。

**第三，这正是大模型擅长的。** 传统 NLP 工具处理这类"长文本 + 非结构化 + 语义理解"任务非常吃力，但大模型恰好擅长：理解语义、提取关键信息、从冗长文本中找到有价值的内容。

### 1.3 ESG 报告分析的三大痛点

| 痛点 | 描述 | 为什么 AI 适合解决 |
|------|------|-------------------|
| **① 报告冗长，官话多** | 百页 PDF，大段定性描述，有用的数据散落各处 | LLM 擅长长文本理解和关键信息提取 |
| **② 披露不完整、口径不一致** | 前几年 ESG 报告并非强制披露，公司只披露"好看的数据"，不利数据一笔带过或干脆不提；不同公司的统计口径也各不相同 | AI 能系统性地交叉比对，明确标注"此处未披露"或"口径不可比"，而人工做这件事极其耗时 |
| **③ 多报告对比难度指数级上升** | 同年同行业 10 家公司的横向对比，或同一公司 3 年的纵向对比，文本总量达到数千页。人工几乎不可能高质量完成 | Agent 可以并行检索、自动对齐、生成结构化对比报告 |

**一句话总结：ESG 报告既有分析价值（价值端），又天然适合用 AI 来干（能力端）。**

**潜在用户与消费场景：**

- **ESG 评级机构**（如 MSCI、中财绿金）：需要批量分析企业 ESG 披露质量，当前依赖人工分析师逐篇阅读。
- **投资机构**（基金、券商研究所）：在投资决策中需要快速评估目标公司的 ESG 风险敞口。
- **企业自身**：对标同行 ESG 表现，发现自身披露短板。
- **监管机构**：核查企业 ESG 披露的完整性和真实性。

## 二、第一版：ReAct Agent —— 一切从"经典"开始

### 2.1 为什么是 Agent，不是单轮对话？

这个任务不是"问答"（Q&A），而是"分析"（Analysis）。区别在于：

- **问答**：用户问一个问题，AI 给出一个答案。一步到位，开箱即用。
- **分析**：用户给定一个目标，AI 需要**自己规划步骤、查阅资料、调用工具、交叉验证、生成报告**。

举例：用户说"帮我对比比亚迪和宁德时代近三年碳排放趋势"，这背后隐含了：

1. 确定"碳排放"具体指哪些指标（Scope 1/2/3？）
2. 获取两家公司 2022/2023/2024 年的相关数据
3. 查阅原始报告，验证数据来源
4. 计算同比变化
5. 分析变化原因（年报原文中的策略描述）
6. 生成结论

这显然需要一个**能调用工具、能多步规划的 Agent**，而不是 ChatBot。

### 2.2 ReAct Agent 的尝试

我首先实现了业界最经典的 Agent 范式：**ReAct（Reasoning + Acting）**。

它的逻辑很直观：

```
Thought: 我需要知道比亚迪的碳排放数据
Action: 查询数据库
Observation: 得到 2022-2024 三年数据
Thought: 还需要宁德时代的数据做对比
Action: 查询数据库
Observation: 得到宁德时代数据
...
Thought: 分析完成，整理报告
Final Answer: [完整分析报告]
```

**效果如何？能用，但不够好。**

### 2.3 核心问题：ReAct Agent 是一个"精致的黑盒"

ReAct Agent 完全依赖 LLM 的推理能力，我只能通过 **prompt** 去约束它的行为。但这带来几个致命问题：

1. **不可控**：prompt 不能 100% 保证 Agent 照着运行。它可能在第三步就偏离了方向，开始胡言乱语。
2. **不可调试**：当 Agent 输出质量差时，我无法定位是哪个环节出了问题——是查询写错了？检索没召回相关内容？还是推理出现了幻觉？
3. **不可优化**：仅通过修改 prompt，很难系统性提升效果。Prompt 优化是"打地鼠"——修好一个 case，可能 break 另一个 case。
4. **没有质量保障**：Agent 说是什么就是什么，没有独立的验证机制来检查它有没有编造数据。
5. **无法评估**：我只能凭感觉判断"这个回答好不好"，没有量化指标来衡量 Agent 到底有多可靠。

**这个困境和业界 Agent 落地困境一模一样**：Agent demo 很炫，但一旦上线就失控。这恰好对应了 AI 评测晋升标准中反复强调的核心矛盾——**你需要一个"评测引擎"来驱动 Agent 的迭代，而不是靠人肉感受**。

## 三、第二版：从 "搭出来" 到 "搭得好" —— 三个维度系统性重构

基于第一版的教训，我意识到：**做一个能跑的 Agent 太容易了，做一个可靠的 Agent 才是真正的挑战。**

我决定从三个维度对整个系统进行系统性重构：

```
┌─────────────────────────────────────────────────────────────┐
│                    Agent 质量工程三支柱                       │
├─────────────────┬──────────────────┬────────────────────────┤
│   支柱一         │      支柱二       │       支柱三           │
│  白盒化架构      │   双层质量保障    │   评测驱动的迭代闭环    │
│  (AI应用能力)    │  (AI评测能力)    │   (AI评测14-16级)      │
├─────────────────┼──────────────────┼────────────────────────┤
│ LangGraph        │ Evaluator-D      │ 多维度评测体系          │
│ Workflow设计      │ (数据质量+Replan) │ Bad Case 深度归因       │
│ 11节点+条件路由   │ Evaluator-O      │ 动态评测集构建          │
│ 并行+降级+修正循环 │ (输出质量+修正)   │ 评测→修复→回归 飞轮    │
└─────────────────┴──────────────────┴────────────────────────┘
```

## 四、支柱一：白盒化架构 —— 让 Agent 的每一步都看得见

### 4.1 设计哲学

我把 Agent 的自主性限制在一个**可控的图结构**中，每个步骤可观测、可调试、可独立优化。

| 维度 | ReAct Agent | LangGraph Workflow |
|------|-----------|-------------------|
| 控制方式 | Prompt约束（软约束） | 图结构+节点函数（硬约束） |
| 可观测性 | 只有最终输出，中间过程不可见 | 每个节点有独立Trace、状态、耗时 |
| 可优化性 | 黑盒调Prompt | 每个节点独立可测、可优化、可替换 |
| 质量保障 | 无 | 双层Evaluator+Re-plan循环 |
| 并行能力 | 顺序执行 | SQL+RAG可真正并行 |

### 4.2 Workflow 设计：核心分析链路 12+ 节点 + 条件路由

```
用户提问
   │
   ├── ① context：理解问题 → 提取公司/年份/指标/意图
   │       │
   │       ├── [knowledge] → 知识问答直答 → memory_updater → END
   │       ├── [clarify]   → 反问用户 → memory_updater → END
   │       └── [complex]   → 进入完整分析流程 ↓
   │
   ├── ② supervisor：制定执行计划（用SQL？用RAG？都要？）
   │
   ├── ③ schema_injector：给SQL Worker准备数据库表结构
   │
   ├── ④ [并行] sql_worker ← → rag_worker
   │       │                     │
   │       │  Text2SQL+安全校验    │  混合检索(向量+BM25→RRF→Reranker)
   │       │  SQLite执行          │  Query改写+实质性议题注入
   │       └─────────┬───────────┘
   │                 ▼
   ├── ⑤ worker_aggregator：汇总双路数据（both_ok / sql_only / rag_only / both_failed）
   │
   ├── ⑥ evaluator_d 🧪：数据质量检查（四层）
   │       │
   │       └── 不合格 → supervisor（Re-plan，调整策略重试）
   │
   ├── ⑦ map_reduce：大文本压缩（RAG召回过长时触发）
   │
   ├── ⑧ synthesizer：生成MSCI框架四层分析报告
   │       │         Layer-1: 数据层 → Layer-2: 驱动因素 → Layer-3: 行业对标 → Layer-4: 风险与合规
   │
   ├── ⑨ disclosure_scorer：披露质量评分（完整性/连续性/可比性/可验证性/具体性）
   │
   ├── ⑩ greenwashing_detector：识别 strong claim 但 evidence 不足的人工核查点
   │
   ├── ⑪ evaluator_o 🧪：输出质量检查（五层）
   │       │
   │       └── 不合格 → synthesizer（局部修正重试，最多2次）
   │
   └── ⑫ memory_updater：保存对话记忆 → 返回用户
```

### 4.3 关键技术决策

**为什么 SQL + RAG 并行？** ESG 分析需要两类信息：结构化数据（碳排放吨数、绿色贷款余额）来自数据库，非结构化证据（减排措施描述、政策承诺）来自 PDF 报告。两者互相独立且互补，并行执行能将单次请求延迟从 T_sql + T_rag 降低到 max(T_sql, T_rag)。

**为什么需要 Re-plan 循环？** 真实场景中，第一次查询可能因各种原因失败——年份范围太窄、公司名拼写不一致、RAG 阈值过严等。Re-plan 机制让 Supervisor 能根据 Evaluator-D 的反馈调整策略后重试，大幅降低"因小失败导致整个请求崩溃"的概率。

**为什么用局部修正而非全文重生成？** Evaluator-O 发现问题时，绝大多数情况下只有个别数字或某个 Layer 有问题。全文重生成不仅浪费 Token（成本），还可能引入新错误。局部修正只 patch 有问题的部分，既高效又安全。

## 五、支柱二：双层质量保障 —— 不能让模型自己评价自己

### 5.1 设计理念

**核心原则：质量保障机制必须独立于生成过程。** 不能用"让模型检查自己的输出"来保证质量——这等于让小偷自己查账。

### 5.2 Evaluator-D：数据质量评估（生成前）

在数据收集完成之后、报告生成之前，做四层检查：

| 检查层 | 方法 | 内容 | 不通过时 |
|--------|------|------|----------|
| **L1: SQL有效性** | 确定性规则 | 数据是否为空？覆盖所有请求年份/公司？缺失率>50%？ | Re-plan |
| **L2: RAG质量** | 分数阈值 | 召回文本数≥2？Reranker最高分≥0.3？ | Re-plan |
| **L3: 双路对齐** | 集合运算 | SQL和RAG覆盖的公司/年份是否有交集？ | 缩小范围到交集 |
| **L4: 口径一致** | LLM辅助 | 横向对比时不同公司指标统计范围是否可比？ | 标注差异/补充检索 |

**缺失数据三级分类（ESG 行业特有逻辑）：**

- **L1（大面积缺失）**：核心指标缺失率 > 50% → 触发 Re-plan
- **L2（局部缺失）**：单一公司/年份缺失 → 标注后继续
- **L3（行业性缺失）**：该指标在整个行业普遍不披露 → 直接跳过，不做无意义重试

### 5.3 Evaluator-O：输出质量评估（生成后）

在报告生成之后、返回用户之前，做五层检查：

| 检查层 | 方法 | 内容 | 对应能力 |
|--------|------|------|---------|
| **结构完整性** | 正则匹配 | MSCI四层结构是否完整？ | 规则化评测 |
| **数字事实性** | 数值匹配 + LLM-as-a-Judge | 报告中每个数字能否在SQL/RAG找到证据？支持百分比/万亿/亿等金融数字归一化比对 | LLM-as-a-Judge |
| **实体正确性** | 正则+规则 | 是否出现用户没问的年份/公司？（区分政策目标年份如"2030年碳中和"） | 实体一致性校验 |
| **趋势一致性** | 数值计算 + LLM语义 | 报告中的趋势判断（上升/下降）是否与数据方向一致？ | 数据-结论对齐 |
| **口径标注** | 关键词窗口匹配 | 不可直接对比的指标是否在附近标注了口径差异？ | 规则化合规校验 |

### 5.4 降级策略：优雅地说"我不知道"

当所有重试和修正都失败后，系统不会返回一个可能是错误的答案，而是返回一个结构化的降级响应：

```
### Layer-1: Data Availability
- 查询对象：XX公司
- 查询范围：2022-2024 / Scope 1排放
- 当前项目数据集未覆盖
  （明确区分"系统不支持"和"公司未披露"，避免误导用户）

### Layer-2: Evidence Check
- 已完成结构化库与报告检索双路径检查
- 均未发现可用于回答该问题的证据

### Layer-3: Safe Conclusion
- 为避免幻觉，本次不输出具体数值
- 建议改查已覆盖公司，或补充原始报告材料
```

这个设计对应了 Agent 可靠性治理的核心诉求：**宁可承认不知道，也不要给用户一个看起来合理但实际错误的答案。**

## 六、支柱三：评测驱动的迭代闭环 —— 从"凭感觉"到"看数据"

### 6.1 为什么需要评测体系

第二版虽然有了双层质量保障，但还有一个关键问题没解决：

> **当系统表现不好时，我不知道"哪里不好"和"为什么不好"。**

我需要一个完整的评测体系来回答三个问题：
1. **好不好？**（整体指标）
2. **哪里不好？**（细粒度归因）
3. **怎么改？**（可操作的优化方向）

### 6.2 评测体系设计

#### 评测维度

| 维度 | 指标 | 说明 |
|------|------|------|
| **可靠性** | Completion Rate | 成功返回有效响应的比例（非 crash/empty） |
| **健壮性** | Rescue Rate | Re-plan或修正后最终成功的比例 |
| **安全性** | Crash Rate / Degraded Rate | 崩溃率 vs 优雅降级率 |
| **效率** | p50/p95/Avg Latency | 端到端耗时分位数 |
| **质量** | Judge Overall (1-5) | LLM-as-a-Judge 综合评分 |
| **真实性** | Judge Faithfulness (1-5) | 回答是否可溯源到证据 |
| **工具可靠性** | Tool Error Rate | SQL/RAG Worker 的失败率 |
| **成本** | Avg Steps / Node Count | 平均执行节点数（代理 Token 消耗） |

#### 评测数据集设计

评测数据集不是随便写几个问题。我从以下维度系统性地构建了覆盖不同场景的 case：

| 分层维度 | 类别 | 举例 |
|---------|------|------|
| **Query Class** | knowledge / complex / clarify | "什么是ESG？" / "比亚迪碳排放趋势" / "帮我查一下" |
| **Intent** | trend / compare / ranking / qa / summary | 纵向趋势 / 横向对比 / 排名 / 问答 / 摘要 |
| **Industry** | new_energy / bank / power | 新能源车 / 银行 / 电力 |
| **边界Case** | 数据缺失 / 口径不一致 / 超长文本 / 公司不在覆盖范围 | 覆盖降级路径 |

#### 对比基线

为了证明我的架构设计的价值，我设置了 ReAct Agent 作为 Baseline，在相同评测集上做对比实验。LangGraph Agent 在 Completion Rate 和 Rescue Rate 上有显著优势——这正是因为有双层质量保障和 Re-plan 机制。

### 6.3 Bad Case 深度归因

常规的评估只告诉你"这个 case 失败了"，但我需要知道**为什么失败**。我设计了自动化归因逻辑：

```
评测失败
   │
   ├── node_trace 为空？ → Agent 崩溃（crash）
   ├── is_degraded？     → 数据不可用（优雅降级）
   ├── evaluator_o 失败？ → 输出质量问题
   │     ├── NUMBER_HALLUCINATION     → 数字无证据支持
   │     ├── DIRECTION_CONTRADICTION  → 趋势判断与数据矛盾
   │     ├── MISSING_LAYER            → 报告结构不完整
   │     ├── ENTITY_HALLUCINATION     → 出现了没问的年份/公司
   │     └── MISSING_SCOPE_ANNOTATION → 未标注口径不一致
   └── 成功但 Judge 评分低？ → 质量问题（需人工 review）
```

**每个节点的耗时分布**也被记录，可以看到哪个节点是性能瓶颈：

```

|----------------|----------|----------|----------|-------|
| context        | 2341     | 2200     | 3500     | 20    |
| supervisor     | 150      | 140      | 220      | 20    |
```

这样的数据让我可以做出**基于数据的优化决策**，而不是凭感觉猜。

### 6.4 评测驱动的迭代闭环（飞轮）

```
          ┌──────────────────────────┐
          │    评测数据集（分层设计）   │
          └───────────┬──────────────┘
                      ▼
          ┌──────────────────────────┐
          │    自动评测执行            │
          │    (LangGraph vs ReAct)   │
          └───────────┬──────────────┘
                      ▼
          ┌──────────────────────────┐
          │    多维度指标统计          │
          │    + Bad Case 归因        │
          └───────────┬──────────────┘
                      ▼
          ┌──────────────────────────┐
          │    生成评测报告            │
          │    (eval_report.md)       │
          └───────────┬──────────────┘
                      ▼
          ┌──────────────────────────┐
          │    针对性优化              │
          │    (调整prompt/架构/参数)   │
          └───────────┬──────────────┘
                      ▼
          ┌──────────────────────────┐
          │    回归评测                │
          │    (确认优化效果)          │
          └──────────────────────────┘
```

这个飞轮对应了 AI 评测 14-16 级标准中的核心要求：
- **"构建科学、多维度、高吞吐的自动化评测体系"**
- **"Bad Case 深度归因：不仅提供评测分数，更要对 Bad Case 进行深度分析"**
- **"打通评测发现弱点 → 数据定向修复 → 模型能力提升的飞轮闭环"**

## 八、项目核心亮点（面试话术）

### 亮点 1：从黑盒到白盒 —— 不是"换了个框架"，是设计哲学的转变

> "第一版我用了 ReAct Agent，能跑但不可控。核心问题是：prompt 是软约束，不能保证行为；出错了不知道哪里错；想优化只能改 prompt 碰运气。所以我决定把它从'自主 Agent'变成'受控 Workflow'——用 LangGraph 的图结构把分析过程拆成 11 个独立的、可观测的、可独立优化的节点。这不是技术选型的问题，而是对 Agent 可靠性的根本性回应。"

### 亮点 2：双层质量保障 —— 质量不能靠模型自觉

> "我设计了两层独立于生成过程的质量保障。Evaluator-D 在生成前检查数据质量，不合格就 Re-plan；Evaluator-O 在生成后检查输出质量，做数字溯源、趋势一致性、口径标注五层校验，不合格就局部修正。这个设计保证了：系统要么给出有据可查的分析，要么明确告诉用户'此处数据不可用'——绝不胡编。"

### 亮点 3：评测驱动的迭代 —— 用数据而不是感觉做决策

> "我构建了一个完整的评测体系：分层评测数据集、LLM-as-a-Judge 评分、Bad Case 自动归因、与 ReAct Baseline 的对比实验。评测跑完后，我能精确知道哪个节点是瓶颈、哪种类型的 query 最容易失败、失败的原因是什么。这形成了'评测 → 诊断 → 优化 → 回归'的闭环。"

### 亮点 4：工程完备性 —— 不只是 demo

> "这个项目除了核心 Agent 逻辑，还做了 FastAPI REST API + SSE 流式响应、Redis 对话记忆、前端 Dashboard、健康检查、全链路 Trace、结构化日志。它不是一个跑在 Jupyter 里的 demo，是一个可以部署、可以观测、可以持续迭代的生产级系统。"
