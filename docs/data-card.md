# ESG-Insight Agent Data Card

> 用途：说明当前数据覆盖范围、数据边界和缺失值处理原则。  
> 更新日期：2026-08-09

---

## 1. 为什么需要 Data Card

ESG Agent 最容易出现的问题不是“不会回答”，而是“在数据没有覆盖时仍然装作知道”。

因此本项目引入 `/api/capabilities` 和 Data Card，把系统知道什么、不知道什么明确暴露出来。

面试讲法：

> 我希望 Agent 不是黑盒全知，而是有边界感。它应该明确告诉用户当前覆盖哪些公司、年份、指标；没有覆盖时要降级，而不是编造。

---

## 2. 数据来源

| 来源 | 形式 | 用途 |
|---|---|---|
| 企业 ESG / 可持续发展报告 | PDF | RAG 原文检索、页码证据、定性描述、绿色承诺 |
| SQLite ESG 指标库 | 结构化表 | 数字指标查询、同比、排序、横向对比 |
| Data Dictionary | Python 映射 / 字典 | 指标别名、中文展示名、任务解析辅助 |

---

## 3. 能力边界接口

接口：

```text
GET /api/capabilities
```

它用于返回：

- 本地 PDF 覆盖情况；
- SQLite 数据覆盖情况；
- 指标字典覆盖情况；
- 当前 Agent 支持的能力；
- 已知边界和限制。

相关代码：

```text
agent/capabilities.py
api/main.py
```

---

## 4. 缺失值处理原则

| 情况 | 含义 | 系统应该怎么答 |
|---|---|---|
| SQL 中没有记录 | 当前结构化库未覆盖或企业未披露 | 说明“未在当前结构化库中找到” |
| RAG 没召回证据 | 当前 PDF 检索未找到相关原文 | 提醒证据不足 |
| 指标值为空 | 可能未披露，不能当作 0 | 输出“未披露/缺失”，不参与趋势计算 |
| 指标值为 0 | 企业披露的数值为 0 | 可以作为事实，但需保留单位和来源 |
| 公司不在 coverage 中 | 当前数据集未覆盖 | 降级，不编造 |
| 年份不在 coverage 中 | 当前年份未覆盖 | 明确年份边界 |

关键原则：

> **缺失不是 0；未覆盖不是表现差；证据不足不能硬下结论。**

---

## 5. 当前支持的任务类型

| 任务 | 是否支持 | 说明 |
|---|---|---|
| 单公司指标查询 | 支持 | 依赖 SQLite 和 PDF 覆盖 |
| 跨年趋势分析 | 支持 | 需要多年份结构化数据 |
| 同行横向对比 | 支持 | 需要统一指标口径，输出可比性提醒 |
| ESG 概念问答 | 支持 | 可走 knowledge 快速出口 |
| 披露质量评分 | 支持 | 基于确定性 Rubric |
| 潜在绿漂风险识别 | 支持 v1 | 识别 claim-evidence mismatch |
| 投资建议 | 不支持 | 不输出买卖建议 |
| 企业真实 ESG 评级 | 不支持 | 仅做报告分析辅助 |
| 法律意义上的绿漂定性 | 不支持 | 只给人工核查点 |

---

## 6. 面试时如何讲 Data Card

> 很多 RAG Demo 的问题是默认自己什么都知道，但金融场景里这很危险。我做了 capabilities endpoint 和 Data Card，让系统显式暴露数据边界。比如用户问未覆盖公司，系统会说当前数据不足，而不是编造数字。这个设计体现的是可靠性和安全边界意识。

---

## 7. 后续可提升方向

- 将 `/api/capabilities` 的输出保存为版本化快照；
- 为每个公司生成覆盖矩阵：公司 × 年份 × 指标；
- 在前端增加“当前问题是否在覆盖范围内”的提示；
- 将 Data Card 接入 Evaluator-D，使数据边界直接影响 re-plan / degraded response；
- 区分“企业未披露”和“系统未采集”两类缺失原因。
