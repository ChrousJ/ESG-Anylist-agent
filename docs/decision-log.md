## D-20260806-01：项目主线从“ESG 问答”收敛为“披露质量与绿漂风险识别”

**问题**：当前项目如果只做 ESG 报告问答，容易显得像通用 RAG Demo，缺乏业务深度和真实落地痛点。

**决策**：将项目主线定义为：面向投资研究 / ESG 分析场景的 ESG 披露质量评估与绿漂风险识别 Agent。

**理由**：

1. ESG 报告长文本、格式不固定、官话多，天然适合 LLM 处理；
2. 披露质量和绿漂风险是 ESG 报告中真实存在的业务痛点；
3. 该方向能体现金融背景 + AI Agent + AI Evaluation 的综合能力；
4. 相比泛问答，更容易设计评测集和量化指标。

**取舍**：

- 不追求覆盖所有 ESG 任务；
- 不做股票推荐和完整 ESG 评级；
- 暂不追求大规模爬虫和实时数据。

**影响**：

后续功能围绕三类任务展开：事实抽取、披露质量评分、绿漂风险识别。

**状态**：accepted

## D-20260806-02：从 ReAct Agent 转向 LangGraph 白盒 Workflow

**问题**：ReAct Agent 虽然实现简单，但在金融文本分析场景中存在不可控、不可调试、不可稳定评测的问题。

**决策**：采用 LangGraph 将 Agent 拆成 context、supervisor、SQL worker、RAG worker、evaluator、synthesizer 等显式节点。

**理由**：

1. 每个节点可观测，可记录 trace；
2. 错误可以归因到意图识别、检索、SQL、生成或评测环节；
3. 可以在节点间加入 evaluator 和重试机制；
4. 更符合真实 Agent 应用落地中对稳定性和可控性的要求。

**取舍**：

- 工作流灵活性低于纯 ReAct；
- 工程复杂度提升；
- 初期开发成本更高。

**影响**：

项目从“能跑的 Agent”升级为“可评测、可调优的 Agent 质量工程”。

**状态**：accepted

## D-20260806-03：采用 SQL + RAG 双通道证据获取

**问题**：ESG 分析同时需要结构化指标和非结构化文本证据，单纯 RAG 或单纯 SQL 都不足。

**决策**：保留 SQL worker 和 RAG worker 并行执行。

**理由**：

- SQL 适合查询已抽取的指标、年份、公司、数值；
- RAG 适合检索 PDF 原文、解释性段落、政策承诺、页码证据；
- 两者互补，可降低幻觉并提高证据覆盖。

**取舍**：

- 需要处理 SQL 与 RAG 结果不一致的问题；
- 需要 evaluator_d 判断数据是否足够支撑生成。

**影响**：

后续 Evaluator-O 的数字事实性校验可以同时对齐 SQL 和 RAG 来源。

**状态**：accepted

## D-20260806-04：引入双层 Evaluator 作为质量保障

**问题**：Agent 如果直接根据检索结果生成报告，容易出现数据缺失、证据不足、数字幻觉和趋势误判。

**决策**：采用双层 Evaluator：

- Evaluator-D：生成前检查数据质量；
- Evaluator-O：生成后检查输出质量。

**理由**：

1. Evaluator-D 能在数据不足时触发 re-plan，而不是硬生成；
2. Evaluator-O 能检查结构完整性、数字事实性、实体一致性和趋势一致性；
3. 双层结构使错误尽可能在返回用户前被发现。

**取舍**：

- 延迟和 token 成本上升；
- evaluator 自身也需要评测和调优。

**影响**：

后续实验需要展示质量提升与成本增加之间的 trade-off。

**状态**：accepted

## D-20260806-05：把评测集作为优先级最高的下一步

**问题**：继续堆功能会导致项目变成技术堆砌，无法证明效果提升。

**决策**：下一阶段优先构建 60-100 条 ESG Agent eval cases，并围绕评测指标驱动开发。

**理由**：

1. 评测集是效果优化和论文实验的基础；
2. AI Evaluation 岗位非常看重 Benchmark、LLM-as-a-Judge、Bad Case 归因；
3. 有评测才能讲清楚每次优化到底提升了什么。

**取舍**：

- 短期功能开发速度变慢；
- 需要人工标注一部分 evidence 和 rubric。

**影响**：

项目进入“评测驱动开发”模式，每个新功能都需要配套 eval case 和指标。

**状态**：accepted

## D-20260809-01：披露质量评分采用确定性 Rubric，而不是纯 LLM Judge

**问题**：披露质量评分如果完全交给 LLM 主观判断，容易出现同一输入多次打分不一致、扣分理由不稳定、难以单元测试和难以接入离线评测的问题。

**决策**：第一版披露质量评分采用确定性 Rubric，将总分拆成五个维度：完整性 30、连续性 20、可比性 20、可验证性 20、具体性 10。

**理由**：

1. 评分逻辑可解释，面试和论文中能讲清楚每一分从哪里来；
2. 结果可复现，便于回归测试；
3. 可以用单元测试覆盖边界情况；
4. 后续仍可把 LLM Judge 作为复核层，而不是唯一评分来源。

**取舍**：

- 规则第一版覆盖不了所有复杂语义；
- 对行业差异和指标口径的理解不如人工专家；
- 需要后续用人工标注样本持续校准权重。

**影响**：

系统新增 `agent/disclosure_quality.py` 与 `agent/nodes/disclosure_scorer.py`，披露质量评分成为 LangGraph 显式节点，并通过 API 和前端展示。

**状态**：accepted

## D-20260809-02：绿漂风险识别收窄为 Claim-Evidence Mismatch

**问题**：直接判断企业是否“真实绿漂”需要监管口径、第三方审计、外部运营数据等证据，仅依赖 ESG 报告和本地数据容易产生误判和合规风险。

**决策**：第一版绿漂风险雷达只识别报告文本中的 claim-evidence mismatch：强 ESG 表述附近如果缺少量化指标、年度进展、同比变化或第三方鉴证，就标记为“潜在人工核查点”。

**理由**：

1. 缩小问题定义，避免对企业做法律意义上的定性；
2. 规则型方法稳定、可解释，适合作为 v1；
3. 输出 evidence gap，方便人工分析师复核；
4. 后续可用人工标注和 LLM-as-a-Judge 提升召回与精度。

**取舍**：

- 不能覆盖所有真实绿漂场景；
- 对隐性选择性披露、复杂口径漂移识别有限；
- 可能把部分正常宣传性语言标为需复核，因此输出必须强调“潜在风险”。

**影响**：

系统新增 `agent/greenwashing.py` 与 `agent/nodes/greenwashing_detector.py`，前端展示 greenwashing radar，并在文档中明确风险边界。

**状态**：accepted
